= Architecture
:toc:
:toclevels: 2

== System boundaries

Impromptu is split into a browser application, an HTTP API, and a realtime media
system. React Router owns navigation and page data. Fastify owns trusted
application decisions and HTTP validation. LiveKit carries room presence and
WebRTC media.

Zod schemas from the API package form the contract between browser and server.
Cloudflare and Envoy sit at the public edge, while OpenTofu describes the
Hetzner and Cloudflare resources.

[source,text]
----
Browser -> Cloudflare -> Envoy -> Fastify
                           `----> LiveKit signaling
Browser ------------------------> LiveKit media
----

The product name is `impromptu` and the production domain is
https://impromptu.social[impromptu.social]. Application code reads both values
from the shared `PRODUCT` constant.

== Repository boundaries

[source,text]
----
apps/api               Fastify API and browser-safe contract export
apps/api/src/accounts  Account registration, login, and sessions
apps/api/src/lobbies   Private lobby persistence and lifecycle
apps/api/src/migrations  Versioned PostgreSQL migrations for every feature
apps/web             React Router application and browser tests
deploy               production and staging containers, configuration, and OpenTofu
Dockerfile           local development image
compose.yaml         local development stack
livekit.yaml         local LiveKit configuration
----

The API is organized by feature. A feature owns its routes and schemas together
with their implementation and tests. Shared process configuration and
application composition stay at the API source root.

The `deploy/` directory is an extractable deployment boundary. It consumes a
prebuilt application image and contains the files needed to provision and run
both server stacks. Application source is not a runtime dependency of that
directory.

== API contracts

The API package owns HTTP methods, paths, request schemas, and response schemas.
TypeScript types are inferred from those schemas. The browser-safe
`@impromptu/api/contracts` export imports neither Fastify nor LiveKit runtime
code.

Fastify validates incoming data and serializes responses against the contract.
The browser parses responses with the same schemas. This keeps static types and
runtime validation together without parallel DTOs or generated client code.

== Realtime authorization

The backend decides whether a participant can publish. The frontend sends the
person's requested role and position, then uses the resulting token. It does not
infer a role from room counts or silently change the request.

LiveKit grants are the security boundary:

[cols="1,1,1,1,1,1",options="header"]
|===
|Role |Join |Subscribe |Publish media |Publish data |Update own metadata

|Debater
|Allowed
|Allowed
|Allowed
|Denied
|Denied

|Spectator
|Allowed
|Allowed
|Denied
|Allowed
|Allowed
|===

The same role policy applies when the client UI is bypassed. LiveKit remains the
source for connected participant presence, and backend allocation must handle
concurrent attempts to claim a limited position.

Room features use LiveKit's official client and React packages.

A participant changes role by joining again with the new intent and the
current lobby's id, so a change made inside a private lobby stays in that lobby.
The backend accepts the id only for a live private lobby of the same topic,
applies the same availability check as the first join, and issues a token with
the new grants; the browser then connects with that token and releases the
previous identity. A rejected change leaves the participant in their current
role with the backend's message.

Topic status lists each connected or reserved participant with their role and
side, so the browser can present debaters and spectators separately without
deciding roles itself.

== Accounts and persistence

Accounts and sessions are stored in PostgreSQL through MikroORM, on the same
connection as private lobbies. `database.ts` opens that connection with every
feature's entities, and each feature keeps its entities and store beside its
routes. Tables change only through the versioned migrations in
`apps/api/src/migrations`, which deployment applies before the application
starts. Tests use in-memory stores with the same interface.

Usernames and email addresses are unique without regard to case: email
addresses are stored in lower case, and a lower-cased username key carries the
username constraint while the username keeps its original spelling. Passwords are hashed with salted scrypt and
never stored or logged in plain text.

Signing in creates an opaque random session token. The browser holds it in an
`HttpOnly`, `SameSite=Lax` cookie, marked `Secure` in production, and the
database stores only its SHA-256 digest with a 30-day expiry. Logging out
deletes the session. `GET /api/auth/session` reports the current account, or
none, while account-only endpoints such as `GET /api/account` answer `401`
without a valid session.

The browser validates forms with the same Zod schemas the API enforces. Field
errors from the API use one `{ message, fieldErrors }` shape, so client and
server validation appear beside the same fields. Account-only pages check the
session in their loader and redirect to the login page with a same-origin
`redirectTo` path.

== Frontend

The web application uses React Router Framework Mode, shadcn/ui, Tailwind, and
LiveKit's React package. Route data APIs handle navigation-bound reads and
mutations. Local component state and LiveKit hooks cover transient interface and
room state.

The API remains the source for application decisions, while LiveKit remains the
source for connected-room state. The frontend does not copy either source into
a global application store.

Private lobby records, creator participant identity, code hashes, and optional
expiry timestamps are stored in PostgreSQL through MikroORM. Join codes are
hashed at rest. Public topic definitions remain static application data. LiveKit
is authoritative for connected participant presence and display names; leaving
a lobby removes the participant from its LiveKit room and releases any pending
side reservation. Database schema changes are applied through versioned
migrations before deployment, not through automatic schema synchronization.

Private join codes expire after 24 hours. Invalid and expired codes are rejected
before a participant token is issued. A valid code does not guarantee that a
requested debater side is still available; in that case the API rejects the
join with a reason and leaves the participant out of the room. Spectating remains
available when both sides are occupied.

Guests join public and private lobbies without signing in. Their chosen display
name is included in the LiveKit token and appears in the room participant list.
Signed-in people have their username suggested as a display name, but lobby
participation and private lobby ownership are not yet tied to an account. Leave requests
release pending side reservations and remove the participant from LiveKit;
repeating a leave request is safe. After a successful leave, the browser returns
to lobby selection.

Fastify serves the compiled SPA in production. Vite provides the development
server and proxies API requests during local development.

== Edge and deployment

Cloudflare provides public DNS, HTTP proxying, and TLS. Envoy is the CNCF origin
gateway and routes application traffic separately from LiveKit signaling.
LiveKit media reaches the host directly because a standard Cloudflare HTTP proxy
does not carry the required media transports.

Production and staging share the Hetzner host and Envoy. They use separate
Compose projects, LiveKit instances, media ports, and Neon database branches.
Staging stays online at `staging.impromptu.social`. Its database branch persists
across deployments; each deployment applies versioned migrations before starting
the new application image.

OpenTofu owns the Hetzner host, firewall, SSH access, Cloudflare DNS records,
origin certificates, and the zone settings required at the edge. Private keys
and API credentials remain outside OpenTofu inputs and state. Successful CI for
the current `main` or `staging` commit gates deployment to its corresponding
environment. Each workflow builds an immutable application image, installs its
runtime configuration, starts its Compose stack, and verifies the public
application and signaling routes. Manual deployment remains available for
initial provisioning and recovery.

The root Compose files are for source development. Server configuration
belongs under `deploy/`, including its Dockerfile, Compose stacks, service
configuration, scripts, environment template, and infrastructure code.

== Verification

The Husky pre-commit hook and GitHub Actions both run `npm run ci`. A failed gate
stops the commit. The command checks formatting, linting, strict TypeScript,
tests, production builds, documentation generation, containers, workflows, and
infrastructure configuration.

The TypeScript version comes from the root `package.json`. Tool compatibility
is resolved by updating or replacing the affected tool rather than holding
TypeScript to an older release.
